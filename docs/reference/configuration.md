# Configuration

agoranomos reads its settings from the `.env` file in the root of the checkout. `./agoranomos init` creates it from `.env.example` and fills in every secret that is empty ([Command line](command-line.md)). Only its owner can read `.env`, and it is never committed.

!!! warning "Keep a copy of `.env`"

    `.env` holds the keys that decrypt the connections Airflow and Metabase save in their databases. Without them, the connections in a restored backup of those databases cannot be decrypted. Keep a copy in a password manager.

    Before an upgrade of Metabase, back up its database as well: [Back up Metabase before an upgrade](#back-up-metabase-before-an-upgrade).

`./agoranomos` reads each setting as Docker Compose does (compose-go 2.16.1, as of October 2026) for lines of the form `KEY=value`: the last line that sets a setting counts, a value in single or double quotes is what is between the quotes, and a value without quotes ends where a space and `#` start a comment, without the blanks and the carriage return at its end, which a `.env` saved with the line endings of Windows has. After an empty value, a space and `#` do not start a comment: Compose reads `KEY= # note` as the value `# note`, and `./agoranomos preflight` stops on such a line, so put a comment on a line of its own. Write each setting at the start of its line, without `export` and without blanks around the `=`, keep each value on one line, and put a value with spaces, a `#` or a `$` in single quotes: Compose expands `$` and reads escapes such as `\"` outside single quotes, and `./agoranomos` does neither.

## Docker Compose

| Setting | Default | What it does |
|---|---|---|
| `COMPOSE_PROJECT_NAME` | `agoranomos` | The name of the Compose project. It starts the names of the containers, networks and volumes. |
| `COMPOSE_PROFILES` | `core,demo,ai` | The profiles that run. `core` is the whole stack in local mode, and `demo` adds the demo: on the first start, the one-shot `demo-init` job runs the demo pipeline and creates a demo dashboard in Metabase ([See the demo](../how-to/see-the-demo.md)). Set `core` to start without it. `ai` adds the container of the MCP servers of the warehouse and of Airflow, in local mode; `./agoranomos ai warehouse\|airflow on\|off` adds it and takes it out ([The MCP servers of the warehouse and of Airflow](#the-mcp-servers-of-the-warehouse-and-of-airflow)). `server` adds the proxy of server mode, and `ops` the `backup` service, which takes a backup every day; `./agoranomos init --server` adds both and takes `ai` out ([Server mode](#server-mode), [ADR-0019](../adr/0019-open-only-metabase-in-server-mode.md); [Backups](#backups), [ADR-0020](../adr/0020-back-up-the-databases-every-day.md)). |
| `COMPOSE_FILE` | `compose.yaml` | The Compose files of the stack. `compose.yaml` runs Airflow with LocalExecutor, which needs no broker. `compose.yaml:compose.celery.yaml` adds the Celery broker and a separate worker (CeleryExecutor), for which 12 GB of memory is recommended ([System requirements](system-requirements.md)). |

| `AIRFLOW_PARALLELISM` | `4` | How many Airflow tasks run at the same time at most, in the whole stack. With CeleryExecutor it caps all workers together: raise it together with `AIRFLOW_WORKER_CONCURRENCY` or the number of workers. |

Each of these processes keeps a connection to the database of the results of Celery, whose role takes at most 20 ([Secrets](#secrets)): keep the sum over all workers at 18 or less. |

## Server mode

Server mode puts Metabase on the internet behind Caddy, with HTTPS, and opens the ports 80 and 443 of the host and no other ([ADR-0019](../adr/0019-open-only-metabase-in-server-mode.md)). Airflow and Metabase stay on `127.0.0.1` too, for SSH tunnels.

`./agoranomos init --server <domain>` turns it on: it sets `AGORANOMOS_SITE_URL=https://<domain>`, adds the `server` and `ops` profiles to `COMPOSE_PROFILES`, and sets `AGORANOMOS_IPV6` and the two rules of Metabase below where they are not set (a plain `init` adds `AGORANOMOS_IPV6=true` to a `.env` that lists `server` and lacks it). To go back to local mode, run `./agoranomos down` first, while `server` is still in `COMPOSE_PROFILES`: Compose stops only the services of the active profiles, so after you take `server` out, the `proxy` container would keep running on ports 80 and 443. Then take `server` out of `COMPOSE_PROFILES` (and `ops`, unless you want the daily backups in local mode too), delete the lines `AGORANOMOS_SITE_URL`, `AGORANOMOS_IPV6`, `METABASE_PASSWORD_COMPLEXITY` and `METABASE_SESSION_TIMEOUT` of `.env`, and run `./agoranomos up`: Metabase then has its address on `localhost` again. If you took `server` or `ops` out first, `./agoranomos up` and `./agoranomos down` stop and remove the `proxy` or `backup` container that is left, and say so; the volume `caddy-data` and the backups stay. A `.env` of server mode from before the backups lists `server` and not `ops`: `./agoranomos preflight` warns about it, and `./agoranomos init --server <domain>` again adds `ops`.

| Setting | Default | What it does |
|---|---|---|
| `AGORANOMOS_SITE_URL` | `http://localhost:` and `METABASE_PORT` | The address of Metabase, which it uses in its links. In server mode it is `https://` and the domain name of the server, which Caddy serves; `./agoranomos init --server <domain>` sets it. It is not in `.env.example`, so that local mode keeps the default. |
| `AGORANOMOS_IPV6` | `false` | `true` or `false`: whether the network `default` of the stack, which Airflow, Metabase and the proxy use, has IPv6, with a subnet of Unique Local Addresses that Docker picks (Docker Engine 27.0.1 or newer; server mode needs 28.0 anyway). `./agoranomos init --server` sets `true`, so that Metabase sees the address of each IPv6 client as it sees that of each IPv4 client: without IPv6 on the network, Docker hands the connection of an IPv6 client to the proxy from the gateway of the network, and the limit of Metabase on failed sign-ins from one address counts all IPv6 clients together ([ADR-0023](../adr/0023-give-the-network-of-the-stack-ipv6.md)). Local mode leaves it `false`, as Metabase listens on `127.0.0.1` only there. A plain `init`, which `up` runs, adds `true` to a `.env` that lists `server` and lacks the setting, and says so. The network carries the label `dev.agoranomos.ipv6` with the same value. Compose recreates a network when anything in its definition changes, and then joins the containers that it keeps to it without the aliases of their services, so `./agoranomos up` and `./agoranomos restore` stop the stack first (`docker compose down`, never with the volumes) when the network that exists lacks the label, has another value in it, or has the other IPv6 setting, and Docker makes the network and the containers together. That happens once for every existing stack, in local mode too, at the first `up` after the release that gave the network the label, and again at each change of the setting; the data stays. Before the stop they build and pull the images, and with `true` they make a network with IPv6 under a name of their own and remove it; if one of these fails, they stop with Docker's error and leave the stack as it is (for the network, `false` is one way out if the error is about IPv6 or `ip6tables`). Not in `.env.example`. |
| `AGORANOMOS_TLS` | `acme` | Where Caddy gets the certificate of the site: `acme`, from the ACME directory below, or `internal`, from its own authority, which no browser trusts, for tests. |
| `AGORANOMOS_ACME_CA` | `https://acme-v02.api.letsencrypt.org/directory` | The ACME directory of Let's Encrypt. For a trial, its staging directory, `https://acme-staging-v02.api.letsencrypt.org/directory`, has higher limits and gives certificates that browsers do not trust. Let's Encrypt issues at most five certificates for the same names in seven days (as of October 2026). |
| `METABASE_PASSWORD_COMPLEXITY` | `normal` | The rule of Metabase for new and changed passwords: `normal`, 6 characters with a digit, or `strong-enough`, at least 15 characters, which `./agoranomos init --server` sets. With `strong-enough`, in local mode as well, a `METABASE_ADMIN_PASSWORD` that you write by hand must have at least 15 characters too, and `./agoranomos preflight` stops on a shorter one, also when Metabase is set up already; the one that `init` generates has 32. `metabase-init` never changes the password of an admin that exists, so for a Metabase that is set up already, first change the password in Metabase (Account settings) to at least 15 characters (with the stack stopped, `docker compose up -d metabase` in this folder starts Metabase alone, with the databases it needs and without the proxy, at `127.0.0.1` on `METABASE_PORT`, which on a server you reach through an SSH tunnel), then put the same value in `.env`; for a new one, write a longer value, or leave it empty for `init` to generate one. Like `AGORANOMOS_SITE_URL`, it is not in `.env.example`. |
| `METABASE_SESSION_TIMEOUT` | none | How long a person stays signed in to Metabase without activity, as JSON: `./agoranomos init --server` sets `'{"amount":24,"unit":"hours"}'`; the unit is `seconds`, `minutes` or `hours`. Empty, Metabase keeps a session until it expires, after two weeks. Not in `.env.example`. |

Caddy keeps its certificates in the Docker volume `caddy-data`, which backups leave out: a lost volume means a new certificate. It sends Let's Encrypt no contact email, as Let's Encrypt has sent no expiration emails since June 2025, and Caddy renews the certificate by itself.

[Deploy on a server](../how-to/deploy-on-a-server.md) walks through it on a new server.

## AI access in Metabase

The level of AI access sets what AI clients may do in Metabase through its MCP server, and what every account may do in the Metabase UI as well ([ADR-0017](../adr/0017-set-ai-access-in-metabase-by-levels.md)). `./agoranomos ai` shows the four settings below, `./agoranomos ai set <level> [--default <level>]` writes them together, and `./agoranomos up` applies them ([Command line](command-line.md#ai)). Change them with the command rather than by hand. `./agoranomos preflight`, which `up` runs, stops in these cases and names the command that sets them right:

- the level is not one that this release offers;
- the default level is not a level from `answers` up, or is higher than the level;
- the two switches do not follow the level.

`metabase-init` checks the same for a start through plain `docker compose`, and fails before it changes anything.

A new installation gets the level `build` and the default level `explore`, from `.env.example`. A `.env` of a release from before the levels gets `off` from `init`, which says how to turn AI access on, so an upgrade widens no access. A setting that is not set, or empty, has the default that `compose.yaml` gives it, which is `off` for the level.

| Setting | Default | What it does |
|---|---|---|
| `METABASE_AI_LEVEL` | `build` | The highest level of AI access that the deployment allows: `off`, `answers`, `explore`, `build` or `build-sql`, each of which adds to the one before it. At `off` the MCP server of Metabase is off. This release offers `off`, `answers`, `explore` and `build`; `build-sql` comes after the first release of the AI layer, and until then SQL from AI clients goes through MCP Toolbox ([The MCP servers of the warehouse and of Airflow](#the-mcp-servers-of-the-warehouse-and-of-airflow)). |
| `METABASE_AI_DEFAULT_LEVEL` | `explore` | The level that every account gets, from `answers` up, and no higher than `METABASE_AI_LEVEL`. It is not used while the level is `off`. |
| `METABASE_MCP` | `true` | Follows the level: `true` from `answers` up. Metabase gets it as `MB_MCP_ENABLED`, and as the master switch of its AI features, `MB_AI_FEATURES_ENABLED`, which the MCP server needs. |
| `METABASE_MCP_SQL` | `false` | Follows the level: `true` only at `build-sql`. Metabase gets it as `MB_MCP_EXECUTE_SQL_ENABLED`, which turns on the SQL that a client writes. |

What each level may do:

| Level | Queries on the marts | Workspace |
|---|---|---|
| `answers` | Runs the saved questions and dashboards of the collections that the account may view, and builds no new query | No access |
| `explore` | Also builds new queries on the marts with the query builder, and saves them in the person's own collection | No access |
| `build` | As `explore` | Curate: creates, changes and trashes questions, dashboards, metrics and documents there |

Above `off`, `metabase-init` sets these permissions on every start, with one line for each change:

- **All Users**, the group of every account, gets the default level:
    - Create queries on the warehouse, and at most that on every other database;
    - View on the root collection and on Reports, and at most View on every other collection;
    - on Workspace and its sub-collections, Curate from `build` up and No access below it.
- **Groups of the setup.** Each level above the default, up to the level of the deployment, has a group: `agoranomos: Explorers`, `agoranomos: Builders`. An admin puts people into them in Metabase, and the setup never changes who is in a group. A group gets the permissions of its level, kept between the default and the level of the deployment when either changes: a group above the level gets the level, and one at or below the default gets the default.
- **Workspace and Reports.** Two collections at the root: Workspace for shared drafts, and Reports for finished work, which everyone views and only admins curate. The setup finds them by their entity IDs, not by name, so you may rename or move them; one in the trash comes back.
- **What stays.** A group that the deployment made itself keeps its permissions, apart from Curate on Reports, which only admins have. Personal collections keep theirs, and the content of the package stays view-only for everyone but admins ([The content of the package](#the-content-of-the-package)).

At `off` the setup changes no permission, also not those that a higher level set before. `./agoranomos ai diff` shows what the next `up` would change in these permissions, and changes nothing ([Command line](command-line.md#ai)).

An AI client connects to the MCP server of Metabase with an OAuth client that `./agoranomos ai connect` registers, and each person signs in with their own account, which is not an admin ([ADR-0031](../adr/0031-register-and-revoke-the-oauth-clients-of-metabase-with-the-script.md)). In server mode the proxy closes registration to the internet and lets a token reach only the MCP server. At `off`, `./agoranomos up` and `./agoranomos ai set off` delete every OAuth client, with its tokens, so that no client keeps access; a start with plain `docker compose` deletes none. `./agoranomos ai clients` lists the clients, and `./agoranomos ai revoke` deletes one ([Command line](command-line.md#ai)).

Metabase OSS records which clients people authorized, but not the calls that the clients make. So, after the permissions, `metabase-init` looks on every start for what the levels do not keep, and `./agoranomos up` looks at the OAuth clients in the application database of Metabase. `up` shows each finding as a warning, which does not stop the start:

- a subscription of a dashboard, or an alert on a question, that sends to an email address that no account of Metabase has, or to Slack or a webhook. The warning names the subscription or the alert by its ID, and an admin checks it in the menu of the dashboard or of the question;
- SQL questions that members of the groups of the setup saved, which no level of this release writes and which keep running, by their IDs;
- above `off`, a group of the setup without members;
- above `off`, an admin account that holds a token of an OAuth client, which has not expired: an AI client works as the account that connected it, so an admin connects with a second account that is not an admin;
- above `off`, an account that holds a token with `mb:full`, the scope of the whole REST API of Metabase, which no client that `ai connect` registers gets. The warning names the client, and `./agoranomos ai revoke` cuts it off.

Above `off`, the last line of `up` also names the groups of the setup and how many people each has, and `./agoranomos ai` shows the same while Metabase runs.

## Backups

`./agoranomos backup` takes a backup of the three databases at any time, and with the `ops` profile, which `./agoranomos init --server` turns on, the `backup` service takes one every day ([ADR-0020](../adr/0020-back-up-the-databases-every-day.md)).

| Setting | Default | What it does |
|---|---|---|
| `AGORANOMOS_BACKUP_DIR` | `./backups` | The folder of the backups. The default folder, `backups/`, is ignored by git; another path is not, unless you ignore it yourself. `init` creates it, open to its owner only. A relative path starts at the checkout, `~/` at your home folder; `preflight` stops on a value that is none of these and not absolute, which Compose would read as the name of a volume. By default the folder is on the disk that holds the data of Docker: on a small server put it on another disk, such as `/mnt/backups`, and `./agoranomos status` says how much room the disk has. |
| `BACKUP_TIME` | `03:00` | With the `ops` profile: the time of the daily backup, as `HH:MM`. A backup that the stack missed, because it was down, comes at its next start. Choose a time when no pipeline runs: a dump holds a shared lock on each table of its database until it ends, and a change of a table by dbt or dlt waits behind it for at most a minute and then fails. No DAG of the base package that changes a table runs at 03:00 UTC: `agoranomos_watcher`, which runs every 15 minutes, reads, and writes the rows of its own table only, which a dump does not hold back ([Alerts](#alerts)). |
| `BACKUP_TZ` | `UTC` | The time zone of `BACKUP_TIME`, such as `Europe/Berlin`. `preflight` checks the name. |
| `BACKUP_KEEP_DAILY` | `7` | How many days back the newest scheduled backup of each day stays; at least 1. |
| `BACKUP_KEEP_WEEKLY` | `4` | How many weeks back, Monday to Sunday, the newest scheduled backup of each week stays. |
| `BACKUP_KEEP_MONTHLY` | `12` | How many months back the newest scheduled backup of each month stays: a year by default ([ADR-0044](../adr/0044-keep-the-core-for-good-and-change-it-by-migrations.md)). |
| `AGORANOMOS_UID`, `AGORANOMOS_GID` | `auto` | The user and the group that write the backups, so that they belong to you: `init` replaces `auto` with yours. `preflight`, `backup` and `restore` stop on 0, root. On Linux they stop too when the backups folder belongs to another user, because the service runs as `AGORANOMOS_UID` and cannot write into a folder of mode 700 that another user owns: a `.env` that you move to another machine keeps the IDs of the first, so set them to `auto` there and run `./agoranomos init`. |

A backup holds the dumps of the databases, the global objects of both instances without passwords, an archive of the extensions folder, the SHA-256 of each file and a manifest, which records the images of the checkout. It does not hold `.env`, whose keys a restore needs, or the certificates of server mode. A backup is as sensitive as `.env`: it holds every row of the warehouse, the hashes of the passwords of the users of Metabase, and the connection details that only the `METABASE_ENCRYPTION_KEY` of this `.env` decrypts. `./agoranomos restore` puts a backup back ([Command line](command-line.md#restore)). The days, weeks and months of the retention are those of UTC.

The retention removes scheduled backups only, after each good backup. A backup that `./agoranomos backup` took, such as the one before an upgrade, and the one that `./agoranomos up` takes before migrations of the core ([The migrations of the core](#the-migrations-of-the-core)), stay until you delete their folders with `rm -r backups/<name>`; `./agoranomos status` lists these backups with their size and age. Take it before you update the checkout with `git pull`: a backup in a container of its own records the images of the checkout as they are when it runs. When the disk is full, every backup fails and the retention removes none: delete old backups to free space.

A backup is written as `.partial-<name>` and renamed when it is complete, so a folder with the name of a backup is a complete one. A stop of the `backup` service during a backup, such as `./agoranomos down`, ends it: the next backup removes the partial folder, and `latest.json`, in the backups folder, keeps the result of the last backup. To turn the daily backups off, take `ops` out of `COMPOSE_PROFILES`; the backups stay ([Server mode](#server-mode) says what `up` and `down` do with the `backup` container that is left).

The `backup` service runs as `AGORANOMOS_UID` and `AGORANOMOS_GID` of the host, so that the backups belong to you. Rootless Docker and `userns-remap`, which map the users of containers to other users of the host, are not supported: the backups would belong to another user.

[Back up and restore](../how-to/back-up-and-restore.md) shows how to schedule, copy and restore them.

## Retention

The service data that grows with each run leaves by itself after a time ([ADR-0044](../adr/0044-keep-the-core-for-good-and-change-it-by-migrations.md)). None of the periods is a setting of `.env`.

| Data | How long it stays | What removes it |
|---|---|---|
| The rows of the database of Airflow: runs, task instances, XComs, asset events, jobs and the log of events | 90 days | `airflow-init`, at each `./agoranomos up` |
| The logs of Airflow, those of the tasks and of the DAG processor, in the volume `airflow-logs` | 30 days | The task `clean_airflow_logs` of the DAG `agoranomos_maintenance`, every day at 04:23 UTC |
| The results of the runs of dbt that elementary records in the schema `ops` | 90 days | The task `clean_ops` of the same DAG, as the role `transformer` |
| The rows of `_dlt_loads` of each raw schema, but those that a load, dlt or the next pin still reads | 90 days | The task `clean_dlt_loads` of the same DAG, as the role `loader` |
| The rows of the loads in the tables of each raw schema, but the journal `_agoranomos_loads` and the tables of dlt | Until a run of the transform accepts their load and account, and a day for a load that did not end | The task `clean_raw` of the DAG `agoranomos_demo_transform`, as `loader`, after each run whose tasks of dbt all succeeded ([Watch the pipeline](../how-to/watch-the-pipeline.md#when-a-run-ends-the-acceptance-and-the-cleanup)) |
| The accepted rows of the kind `window` of `core.loads`, but those that a run or a load still reads | 13 months | The task `clean_core_loads` of the same DAG, as `transformer` |
| The journals of restatements of the core, by month | 13 to 14 months | The task `drop_old_journal_months` of the same DAG, through `core.drop_partition` |
| The Airflow Variables `cosmos_xcom_backup__…` that the watcher mode of Cosmos leaves | 90 days after their run | The task `clean_cosmos_variables` of the same DAG |
| The records of the maintenance in `ops`: `ops_disk` and `ops_maintenance_steps`, and `ops_core_totals` | 90 days, and 13 months | The tasks that write them |
| The log of the queries of Metabase, the table `query_execution` | 90 to 121 days | Metabase itself, as `compose.yaml` sets `MB_AUDIT_MAX_RETENTION_DAYS=90` |

The DAG `agoranomos_maintenance` is unpaused when Airflow first sees it, unlike the other DAGs of the base package, so that its tasks run with no one to start them, and it runs at once on the first start, where its first task can come before the API server of Airflow answers, fail, and run again five minutes later. A pause that you set in the Airflow UI stays, and stops its tasks. A task that fails leaves the run failed in Airflow, and the run of the next day does the work again.

- **The database of Airflow.** A task has no access to the database of Airflow, so `airflow-init` runs `airflow db clean` at each start, with no archive tables. The cleanup runs only then: a stack that runs for months without `./agoranomos up` keeps growing, by about 0.3 GB a year at 300 tasks a day. It gives no room back to the disk either: PostgreSQL keeps the free space inside its files, and the rows that follow take it, so the database stops growing and does not shrink. Some rows stay whatever their age: the DAGs themselves, as `airflow-init` runs before the DAG processor and every DAG would look old to it after a stop of more than 90 days, and come back paused; the newest run of each DAG that its schedule or an asset started; the last version of each DAG; and the runs of `agoranomos_demo_history`, with their tasks, as `demo-init` triggers the only one, `airflow db clean` keeps no run that someone triggered, and `demo-init` would run the demo pipeline again without it. A run older than 90 days that still runs goes too, and its task stops; no run of agoranomos lasts that long. With Airflow 3.3.2 the cleanup takes two calls of `airflow db clean`, as a call that leaves out the rows of a DAG fails on three tables and passes over the rows that belong to no DAG, so `./agoranomos logs airflow-init` shows a warning that the first call did not clean the table `deadline`, which the second cleans. A call that fails stops nothing: `airflow-init` prints one line, `airflow-init: the database of Airflow keeps its old rows of …`, with the tables and the error, and the start goes on, and the next start deletes those rows.
- **The logs of Airflow.** The task deletes each file of a log older than 30 days, and the folders that this leaves empty a day later, as the deletion of a file gives its folder a new time. A run stays 90 days, so a run between 30 and 90 days old shows in Airflow without its logs: Airflow then answers `Log file not found on worker`, which means here that the log is gone.
- **`ops`.** The Ops collection reads the last 30 days ([Watch the pipeline](../how-to/watch-the-pipeline.md)), and the task keeps 90, in the tables of elementary that grow with each run: `dbt_invocations`, `dbt_run_results`, `elementary_test_results`, `test_result_rows` and `dbt_source_freshness_results`, by their column `created_at`. The other tables of elementary hold the project as it is, its models, tests and sources, and replace their rows. `data_monitoring_metrics` and `schema_columns_snapshot` grow only with the tests of anomalies and of schema changes of elementary, which the project does not use, so they stay empty, and the task leaves them alone.
- **Metabase.** Metabase 0.64.1 takes `MB_AUDIT_MAX_RETENTION_DAYS` from the environment alone, at 30 days at least, and does not show it in its API; without it, it would keep 720 days. The open-source image writes neither `audit_log` nor `view_log`, which the setting also covers. `query_execution` has a partition for each month, and once the whole table is on partitions, a month goes whole when it ends before the limit: a row stays 90 to 121 days.
- **The table `_dlt_loads`** of each raw schema keeps 90 days, and never by the date alone, as a load, dlt and the pin read it ([The data model](data-model.md#the-raw-layer)): after a stop of more than 90 days every row looks old, and a deletion of all of them would keep a load that no run has pinned out of every run and make the next load of Google Ads take its 36 months again. So the task keeps, whatever their age, the row of the newest whole load of the schema, which a load reads to know that its schema holds one; the row of the load of the newest state of each pipeline, from which dlt restores the state; the rows of the loads that hold the newest day and the last day loaded of each account in the journal `_agoranomos_loads`, from which the next load starts its window; and the rows of the loads that `core.loads` does not hold yet, which the next pin takes. The journal and the rows of raw keep theirs, which the cleanup of raw after the acceptance of a load is to remove ([#203](https://github.com/agoranomos/agoranomos/issues/203)).
- **`core.loads`** keeps a pinned row whatever its age, as no run has accepted it and staging reads its rows, and deletes an accepted one of the kind `window` 13 months after its load ended ([ADR-0046](../adr/0046-pin-the-loads-before-the-transform-and-accept-them-before-the-cleanup.md)), but the newest accepted load of the kind `window` of each account, from whose last day a load is to start, an accepted load newer than the oldest pinned load of its account, which staging can still read, and a load whose row `_dlt_loads` still holds, which the next pin would take again as a new load. A row of the kind `history` stays, as the history of Google Ads plans its next portion from the windows that `core.loads` holds ([Connect Google Ads](../how-to/connect-google-ads.md#when-the-history-arrives)). Nothing accepts a load yet, so the task deletes nothing today.
- **The journals of restatements** go by month: a month goes once the whole of it is older than 13 months, through `core.drop_partition`, which waits at most 2 seconds for its lock. A month that a reader or a writer holds stays to the next run.
- **The Variables of Cosmos.** The watcher mode of Cosmos 1.16.0 keeps the backup of the XComs of its producer in the task store of Airflow, and writes a Variable `cosmos_xcom_backup__<DAG>__<group>__<run>` only when its last write to the task store failed; a run that failed leaves it ([astronomer/astronomer-cosmos#2823](https://github.com/astronomer/astronomer-cosmos/issues/2823)). A Variable has no time of its own, so the task takes the moment in the ID of its run, and deletes those of the runs older than 90 days, when `airflow-init` has deleted the run itself; one whose name holds no ID of a run that Airflow made stays. The transform of the base package does not run in the watcher mode yet ([#203](https://github.com/agoranomos/agoranomos/issues/203)), so only a DAG of a deployment can leave one, which [Settings fixed in `compose.yaml`](#settings-fixed-in-composeyaml) advises against.

## The MCP servers of the warehouse and of Airflow

Two more MCP servers run in local mode, for an AI client on the same machine, such as Claude Code in the checkout ([ADR-0030](../adr/0030-ship-three-mcp-servers-in-v0-3-0-with-the-stdio-servers-in-local-mode.md)):

- **The warehouse**, MCP Toolbox for Databases 1.15.0. It signs in as the role `ai_reader`, which reads the views of `marts` and nothing else, in sessions that start read-only, with a statement timeout of one minute and at most three connections ([Secrets](#secrets)). Its tools are in `ai/tools.yaml`: `list_tables` and `describe_table`, which list the views of `marts` and their columns, with the descriptions of the dbt project, and `execute_sql`, which runs one statement.
- **Airflow**, astro-airflow-mcp 0.9.1, in its read-only mode, which refuses every tool that writes, such as `trigger_dag` or `pause_dag`, before the call reaches Airflow. It signs in as the Airflow user `ai`, which has the role Viewer alone: it reads the DAGs, their runs and the logs of their tasks, and gets no connections, variables or configuration of Airflow. `airflow-init` gives the user that role and the password of `.env` on every start, so a role or a password changed in the Airflow UI goes back.

Both run in one container, `ai`, of the `ai` profile, which opens no port and reaches only `warehouse-db` and the API of Airflow, with no route to the internet. An AI client starts a server with `./agoranomos mcp warehouse` or `./agoranomos mcp airflow`, which speaks MCP on its standard input and output, and `.mcp.json` in the checkout gives Claude Code both ([Command line](command-line.md#mcp)). The container holds the passwords of `ai_reader` and of the user `ai`, and no other. Its memory limit, `AI_MEMORY`, fits one session of a client at a time: a second session at the same moment can reach it, and the kernel then stops a process of the container and of no other service. Toolbox holds the whole answer of a query in memory, so a statement that returns a large table can reach the limit as well.

Each server has two limits that do not depend on each other: its switch, and the account behind it. While a switch is off, its server does not start, `ai_reader` cannot sign in, and the Airflow user `ai` is deleted.

| Setting | Default | What it does |
|---|---|---|
| `WAREHOUSE_MCP` | `true` | `true` lets the MCP server of the warehouse start, and `ai_reader` sign in. |
| `AIRFLOW_MCP` | `true` | `true` lets the MCP server of Airflow start, and keeps the Airflow user `ai`. |

`./agoranomos ai warehouse on` or `off`, and `./agoranomos ai airflow on` or `off`, set a switch and keep the `ai` profile listed while a switch is on, and `./agoranomos up` applies it ([Command line](command-line.md#ai)). A new installation gets both on in local mode. A `.env` of a release from before them gets both off from `init`, and its `COMPOSE_PROFILES` stays as it was, so an upgrade widens no access. `./agoranomos init --server` turns both off and takes `ai` out: in server mode AI clients reach Metabase over HTTPS ([AI access in Metabase](#ai-access-in-metabase)). `./agoranomos preflight`, which `up` runs, stops when a switch is not `true` or `false`, when server mode lists `ai` or has a switch on, and when `ai` is listed while both switches are off. A switch that is on while `COMPOSE_PROFILES` does not list `ai`, as with `COMPOSE_PROFILES=core`, runs no server, and `./agoranomos ai` shows it as off.

## Alerts

The stack sends an alert through [Apprise](https://github.com/caronc/apprise) when a run of a DAG fails, and when the DAG `agoranomos_watcher`, every 15 minutes, finds an account in quarantine or late, a backup that failed or is late, or a disk with less than 10 GiB free ([ADR-0045](../adr/0045-send-alerts-from-airflow-through-apprise.md), [Get alerts](../how-to/watch-the-pipeline.md#get-alerts)).

| Setting | Default | What it does |
|---|---|---|
| `AGORANOMOS_ALERT_URLS` | empty | One or more addresses of Apprise, separated by spaces or commas, such as `tgram://<bot-token>/<chat-id>` for Telegram or `slack://<token-a>/<token-b>/<token-c>/#<channel>` for Slack, in single quotes. Empty, nothing is sent. Only the scheduler and the service that runs the tasks get it; it is commented out in `.env.example`, as its empty settings are the secrets that `init` generates. |

- **Who sends.** The plugin `agoranomos_alerts` of the Airflow image sends the alert of a failed run from a thread of the scheduler, and the task of `agoranomos_watcher` the alerts of its checks; each address waits at most the timeouts of Apprise 1.13.1, 4 seconds to connect and 4 to read, which an address can change with `cto=` and `rto=`. A message leaves through the network `default` of the stack, which reaches the internet; the databases stay on the internal network.
- **What the watcher keeps.** It connects as `transformer`, which owns the schema `ops`, and keeps what it has seen and sent in the table `ops.alert_state`, which it creates on its first run: one row for each kind, subject and reason, with when the problem began, when an alert last named it, and when it went away while that alert has not gone out. The table holds codes, IDs and times; `metabase_reader` and `ai_reader` cannot read it, and no role gets a new right for it.
- **The status of the backups.** The `backup` service of the `ops` profile writes, every minute, the time of the check, the start of the service, the result of its last run and the end of its last good backup into `status.json` of the volume `backup-status`, which every user may read and only that service may write; the Airflow services mount it read-only at `/opt/agoranomos/backup-status`. A backup does not hold the volume, which the next minute writes again.

## Memory limits

Every service has a memory limit, also for swap, so that the stack stays within the memory of [System requirements](system-requirements.md) and, on the recommended memory (8 GB, or 12 GB for the CeleryExecutor variant), a service that runs short of memory cannot take it from the others ([System requirements](system-requirements.md#memory-limits) says what holds on the minimum of 6 GB). The limits of the services that run all the time are these settings, with defaults from measurements on the demo; those of the one-shot setup jobs are fixed in `compose.yaml`. A value is a number of MiB with `m`, or of GiB with `g`: `preflight` stops on a number without a unit, which Compose would read as bytes, and on a size below 6 MiB, the smallest limit that Docker accepts.

| Setting | Default | Service |
|---|---|---|
| `WAREHOUSE_DB_MEMORY` | `384m` | `warehouse-db`, the warehouse; the settings of PostgreSQL follow it ([below](#the-settings-of-postgresql-of-the-warehouse)) |
| `PLATFORM_DB_MEMORY` | `512m` | `platform-db`, the databases of Airflow and Metabase |
| `AIRFLOW_APISERVER_MEMORY` | `512m` | `airflow-apiserver` |
| `AIRFLOW_DAG_PROCESSOR_MEMORY` | `640m` | `airflow-dag-processor`, which renders the transform DAG from the manifest of dbt each time that it parses it (below) |
| `AIRFLOW_TRIGGERER_MEMORY` | `512m` | `airflow-triggerer` |
| `AIRFLOW_TASKS_MEMORY` | `1280m` | The service that runs the Airflow tasks: `airflow-scheduler` with LocalExecutor, `airflow-worker` with CeleryExecutor |
| `METABASE_MEMORY` | `2176m` | `metabase`; half of it is the heap of Java |
| `PROXY_MEMORY` | `256m` | Server mode only: `proxy`, the Caddy in front of Metabase |
| `BACKUP_MEMORY` | `256m` | With the ops profile: `backup`, the daily backups |
| `AI_MEMORY` | `384m` | With the ai profile, in local mode: `ai`, the MCP servers of the warehouse and of Airflow, for one session of a client |
| `AIRFLOW_SCHEDULER_MEMORY` | `640m` | Only with CeleryExecutor: `airflow-scheduler`, which then runs no task |
| `BROKER_MEMORY` | `256m` | Only with CeleryExecutor: `broker` |

When a service needs more, raise its limit in `.env` and run `./agoranomos up`, which starts it again with the new limit. A one-shot job has no setting here: [System requirements](system-requirements.md#when-a-service-reaches-its-limit) says how one that reaches its limit shows, and what to do. The tasks of heavier pipelines need more than the demo, and so do more tasks at the same time: with LocalExecutor, up to `AIRFLOW_PARALLELISM` tasks run in the scheduler at once, so raise `AIRFLOW_TASKS_MEMORY` with it. Each limit that you raise needs memory on the machine as well: [System requirements](system-requirements.md#memory-limits) says how the defaults add up. When a service reaches its limit, the kernel stops one of its processes ([System requirements](system-requirements.md#when-a-service-reaches-its-limit)).

## The settings of PostgreSQL of the warehouse

`WAREHOUSE_DB_MEMORY` sets more than the limit of a container: `./agoranomos` computes the settings of PostgreSQL of `warehouse-db` from it, and the size of the `/dev/shm` of the container, and passes them to the server through the `command` of the service in `compose.yaml` on every call of Docker Compose ([ADR-0040](../adr/0040-size-the-stack-by-profiles-and-derive-the-settings-of-postgresql.md)). The limit of a container holds the shared memory of PostgreSQL, the private memory of each of its processes and the page cache of the files of the database at once, so the settings of the image, made for a host with more memory than the limit, do not fit it: with them, a limit of 3 GiB kept `shared_buffers` at 128 MB and `effective_cache_size` at 4 GB, and the 64 MB of `/dev/shm` that Docker gives a container ran out under parallel queries, which failed with `could not resize shared memory segment`. With the formulas, one number sets the database: raise the limit, and the cache and the memory of each query follow.

| Setting | Formula | 384 MiB | 1.5 GiB | 3 GiB | 16 GiB |
|---|---|---:|---:|---:|---:|
| `shared_buffers` | A quarter of the limit, at least 128 MB | 128 MB | 384 MB | 768 MB | 4 GB |
| `effective_cache_size` | Two thirds of the limit | 256 MB | 1 GB | 2 GB | 10.7 GB |
| `work_mem` | The limit / 192, from 4 to 32 MB | 4 MB | 8 MB | 16 MB | 32 MB |
| `maintenance_work_mem` | The limit / 12, from 64 to 512 MB | 64 MB | 128 MB | 256 MB | 512 MB |
| `autovacuum_work_mem` | Half of `maintenance_work_mem` | 32 MB | 64 MB | 128 MB | 256 MB |
| `max_parallel_workers_per_gather` | 0 below 1 GiB, 1 below 16 GiB, then 2 | 0 | 1 | 1 | 2 |
| `autovacuum_max_workers` | 2 below 1 GiB, then 3 | 2 | 3 | 3 | 3 |
| `max_wal_size` | 1 GB below 1 GiB, 4 GB below 16 GiB, then 8 GB | 1 GB | 4 GB | 4 GB | 8 GB |
| `checkpoint_timeout` | 15 minutes below 8 GiB, then 30 | 15 min | 15 min | 15 min | 30 min |
| `autovacuum_vacuum_cost_limit` | 1,000 below 16 GiB, then 1,500 | 1,000 | 1,000 | 1,000 | 1,500 |
| `max_locks_per_transaction` | Always 128, for a warehouse of many partitions | 128 | 128 | 128 | 128 |
| `max_connections` | Always 100 | 100 | 100 | 100 | 100 |
| `random_page_cost` | Always 1.1, the cost of a random read on an SSD | 1.1 | 1.1 | 1.1 | 1.1 |
| `shm_size` of the container | The limit / 6, from 64 MB to 1 GB | 64 MB | 256 MB | 512 MB | 1 GB |

The sizes are in the MB and GB of PostgreSQL, which are MiB and GiB, and `./agoranomos` passes them in MB: `4096MB` for the 4 GB of the table, `10922MB` for the 10.7 GB. A unit test checks that the formulas give the values of the table and that the worst case of each limit fits it ([System requirements](system-requirements.md#memory-limits)), and a stack test asks the running server with `SHOW`. The settings that do not depend on the limit stay as they are: `jit` is off for the database `warehouse`, which `db-init` sets with `ALTER DATABASE` on every start ([System requirements](system-requirements.md#memory-limits)), and `io_method` is `worker`, the default of PostgreSQL 18, as the seccomp profile of Docker blocks `io_uring`. `platform-db`, the databases of Airflow and Metabase, keeps the settings of its image.

A value in `.env` wins over the formula. Each setting has a setting of `.env`, `WAREHOUSE_DB_` and its name in capitals: `WAREHOUSE_DB_SHARED_BUFFERS`, `WAREHOUSE_DB_EFFECTIVE_CACHE_SIZE`, `WAREHOUSE_DB_WORK_MEM`, `WAREHOUSE_DB_MAINTENANCE_WORK_MEM`, `WAREHOUSE_DB_AUTOVACUUM_WORK_MEM`, `WAREHOUSE_DB_MAX_PARALLEL_WORKERS_PER_GATHER`, `WAREHOUSE_DB_AUTOVACUUM_MAX_WORKERS`, `WAREHOUSE_DB_MAX_WAL_SIZE`, `WAREHOUSE_DB_CHECKPOINT_TIMEOUT`, `WAREHOUSE_DB_AUTOVACUUM_VACUUM_COST_LIMIT`, `WAREHOUSE_DB_MAX_LOCKS_PER_TRANSACTION`, `WAREHOUSE_DB_MAX_CONNECTIONS`, `WAREHOUSE_DB_RANDOM_PAGE_COST` and `WAREHOUSE_DB_SHM_SIZE`. `.env.example` lists them commented out, each with one line that says what it does and the value of the default limit, and `./agoranomos init` adds none of them to `.env`. A size takes the units of PostgreSQL, such as `512MB` or `4GB`, a time its units too, such as `30min`, and `WAREHOUSE_DB_SHM_SIZE` the units of the memory limits, such as `256m` or `1g`. An empty setting takes the formula. `preflight` stops on a value of another shape than a number with a unit after it, and on a `WAREHOUSE_DB_SHM_SIZE` that is not a memory size; PostgreSQL checks the rest, and when it refuses a value the service does not start, and `./agoranomos logs warehouse-db` names the setting. A value that you set has a worst case of its own to count: the formula no longer keeps it within the limit.

A change of the limit or of a value reaches the server at the next `./agoranomos up`, which starts the service again, as these settings need a restart. `./agoranomos status` shows the limit and the `shared_buffers` that `.env` gives, and warns while the running server has another `shared_buffers` ([Command line](command-line.md#status)). A `docker compose` that runs without `./agoranomos`, such as `docker compose restart warehouse-db`, keeps the container as it is; `docker compose up` without the script would start the service with the defaults of `compose.yaml`, which are the values of the default limit, and with the values of `.env`, which Compose reads itself: start the stack with `./agoranomos up`.

## Settings fixed in `compose.yaml`

Some settings are not in `.env`, because changing them is a decision and not a preference. They are environment variables in `compose.yaml`, and a value from an environment variable wins over any value saved in the application.

The AI switches of Metabase are environment variables in `compose.yaml`, so that nobody changes them in Metabase, admins included.

- **The MCP server and SQL.** The MCP server, with the registration of its OAuth clients and the master switch `MB_AI_FEATURES_ENABLED` that it needs, follows the level of AI access in `.env` ([AI access in Metabase](#ai-access-in-metabase)), and so does the SQL that a client writes, `MB_MCP_EXECUTE_SQL_ENABLED`.
- **Always off.** `MB_AGENT_API_ENABLED`, `MB_METABOT_ENABLED` and `MB_EMBEDDED_METABOT_ENABLED` are `false` at every level, which keeps the Agent API and Metabot off ([ADR-0031](../adr/0031-register-and-revoke-the-oauth-clients-of-metabase-with-the-script.md)).
- **Admin > AI.** The switch there has no effect while the variables are set. Changing it saves a value that would apply if a variable were removed, so leave it alone.

The switches do not cover the keys of LLM providers, which Metabase uses for its own AI features, such as Metabot and the generation of SQL. Metabase 0.64 keeps them in a list of provider connections, to which an admin can add, in Admin > AI and whatever the switches say, a connection with the key of one of eleven providers, such as Anthropic, OpenAI or Google. An Anthropic key also opens `/api/llm/generate-sql`, which does not read the master switch, as in Metabase 0.63. So `compose.yaml` also sets `MB_LLM_PROVIDERS` to an empty list, `[]`: the list then comes from the environment, and Metabase refuses to change it, in Admin > AI and through its provider API, with a message that names the variable (checked on Metabase 0.64.1, as of October 2026). The lock covers the provider API only. The older setting of each provider, such as `llm-anthropic-api-key` or `llm-openai-api-key` (`PUT /api/setting/…`), still saves a value into the stored list, which has no effect while the variable is set. While the variable is set, Metabase neither shows that stored list nor lets anyone clear it through its API, and the list applies as soon as the variable is removed: a change that removes `MB_LLM_PROVIDERS` should check Admin > AI at the first start without it, which is when that list shows. A variable of one provider, such as `MB_LLM_ANTHROPIC_API_KEY`, would still add a connection; `compose.yaml` sets none, and the stack tests check that the list is empty.

A query of Metabase ends after 5 minutes, `MB_DB_QUERY_TIMEOUT_MINUTES` in place of its default of 20, as the `statement_timeout` of its role `metabase_reader` does, which stays as a second fuse. A query that finds all 15 connections of the pool to the warehouse in use waits 30 seconds for one, `MB_JDBC_DATA_WAREHOUSE_CONNECTION_POOL_CHECKOUT_TIMEOUT_MS` of `30000`, and then fails with an error, where the default of `0` waits with no limit ([ADR-0037](../adr/0037-serve-the-marts-as-views-over-the-core.md)).

Metabase keeps the addresses of its users at home too. On a sign-in from a new device, Metabase 0.63 and 0.64 send the IP address of the sign-in to `get.geojs.io`, a service on the internet, to name its place in an email to the user. `MB_SEND_EMAIL_ON_FIRST_LOGIN_FROM_NEW_DEVICE=false` turns that email off, and the question with it. The stack sets up no email server, so no email is lost; if you set up email in Metabase, it still sends no email about a sign-in from a new device, because this setting can be changed only from the environment. The login history in Account settings still asks where each address is, so `compose.yaml` also gives the container of Metabase the name `get.geojs.io` for its own address, where nothing listens: the question reaches no one, the login history shows no place, and the log of Metabase has an `ERROR` line, `Error geocoding IP addresses: Connection refused`, each time that someone opens the login history (checked on Metabase 0.64.1, as of October 2026). `MB_AI_EVAL_CAPTURE=false` keeps off a feature of Metabase 0.64 that would write the traces of its AI features, prompts and answers with the data that they carry, into files for an admin to read; it is off by default, and it can be turned on only from the environment.

dlt, dbt and Cosmos send anonymous usage statistics by default, and four variables in `compose.yaml`, which the Airflow image sets too, turn that off: `RUNTIME__DLTHUB_TELEMETRY=false` for dlt, `DBT_ENGINE_SEND_ANONYMOUS_USAGE_STATS=False` for dbt, `AIRFLOW__COSMOS__ENABLE_TELEMETRY=False` for Cosmos, and `DO_NOT_TRACK=1`, which dbt and Cosmos also honor. The dbt project says the same with `send_anonymous_usage_stats: false` in `dbt/dbt_project.yml`. Metabase reports nothing to its makers either: `MB_ANON_TRACKING_ENABLED` and `MB_CHECK_FOR_UPDATES` are `false`.

A connection of Metabase to a database may go to a private network, where the warehouse is, or to a public address on the internet, but not to a loopback or link-local address, such as the metadata service of a cloud at `169.254.169.254`, or to another address that is neither private nor public, such as the documentation range `192.0.2.0/24` (checked on Metabase 0.64.1, as of October 2026): `MB_WAREHOUSE_ALLOWED_NETWORKS=allow-private`, which also covers the SSH tunnels of connections and the URLs of their authentication providers. Metabase reaches the internet only for what an admin sets up, such as email or Slack, which agoranomos does not set up ([ADR-0021](../adr/0021-leave-the-outgoing-traffic-of-metabase-open.md)). In server mode the proxy closes the two endpoints of Metabase that forward requests to the servers of Metabase without a sign-in, `/api/analytics-proxy` and `/api/product-feedback`.

In server mode the proxy also keeps the OAuth server of Metabase to its MCP server ([ADR-0031](../adr/0031-register-and-revoke-the-oauth-clients-of-metabase-with-the-script.md)):

- **Registration.** It answers 404 to every path that begins with `/oauth/register`, where any client could register itself with no sign-in, also with `mb:full`, the scope that reaches the whole REST API of Metabase.
- **Tokens.** It refuses with 403 a request that carries an `Authorization` header on every path but `/api/mcp`, so that an OAuth token reaches the MCP server and nothing else of Metabase. The UI of Metabase signs in with a cookie and sends no such header.
- **Clients with a secret.** A client that sends its secret in that header to the token endpoint (`client_secret_basic`) gets no token through the proxy. The clients that `./agoranomos ai connect` is to register have no secret.

dlt reads no settings or secrets from Airflow Variables: `PROVIDERS__ENABLE_AIRFLOW_SECRETS=false` is set in `compose.yaml`, and in the Airflow image too. Inside an Airflow task, dlt would otherwise also take its settings from Variables, and a person who may edit them, such as a user with the Op role of Airflow, could redirect a pipeline: for example, send the connection of a load, with its password, to another host. So a DAG in the extensions folder ([ADR-0013](../adr/0013-keep-extensions-apart-from-the-base-package.md)) that follows dlt's guide for Airflow cannot keep its settings in a `dlt_secrets_toml` Variable, which dlt ignores here: the pipeline takes them from environment variables instead.

The two caches from which Cosmos renders the tasks of dbt stay out of Airflow Variables: `AIRFLOW__COSMOS__ENABLE_CACHE_DBT_LS=False` and `AIRFLOW__COSMOS__ENABLE_CACHE_DBT_YAML_SELECTORS=False` are set in `compose.yaml`, and in the Airflow image too. By default Cosmos saves the output of `dbt ls`, from which it renders the tasks of dbt and their arguments, in a Variable named `cosmos_cache__<DAG>__<task group>`, and the YAML selectors of a dbt project the same way: a person who may edit Variables could then change what a dbt task runs. A `cosmos_cache__` Variable that was saved before is no longer read, and you can delete it.

Cosmos does not run `dbt ls` either: it renders the tasks of the transform DAG from the manifest of the dbt project, which the one-shot job `metadata-export` writes on every start into the volume `dbt-manifest`, which the Airflow services mount read-only ([ADR-0027](../adr/0027-load-the-dbt-project-into-cosmos-from-a-manifest.md)). So a change of the dbt project, such as a new model, reaches Airflow at the next `./agoranomos up`, and a dbt project that dbt cannot read stops the start: `./agoranomos logs metadata-export` shows why. The DAG processor parses a DAG file that has not changed again every five minutes, where Airflow's default is every 30 seconds: `compose.yaml` sets `AIRFLOW__DAG_PROCESSOR__MIN_FILE_PROCESS_INTERVAL=300`. A new DAG file in the extensions folder shows up within about a minute, as the DAG processor looks for new files every minute (`AIRFLOW__DAG_PROCESSOR__REFRESH_INTERVAL=60`), and a change to a DAG file within seconds, since Airflow parses a file again as soon as it has changed since its last parse (Airflow 3.3.2, as of October 2026). To have a DAG parsed sooner, choose **Reparse Dag** at the top of its page in Airflow, or call `PUT /api/v2/parseDagFile/{file_token}` with the `file_token` that `GET /api/v2/dags/{dag_id}` returns.

The tasks of dbt, one for each model, each seed and each snapshot of the versions of the core, which builds it and runs its tests ([ADR-0028](../adr/0028-build-each-node-of-dbt-with-its-tests-in-one-task.md)), run in the pool `dbt` of Airflow, at most two at a time, whatever `AIRFLOW_PARALLELISM` allows: each is a process of dbt of its own, and they share the memory of the container that runs them: the scheduler with the LocalExecutor, the worker with the CeleryExecutor. `airflow-init` sets the pool on every start, so an edit of its size in the Airflow UI does not last. It sets the pool `demo_load` the same way: the loads of `agoranomos_demo_history` and `agoranomos_demo_daily` run in it one at a time, so that two loads never replace the days of a platform at the same time.

A DAG in the extensions folder should not use two features of Cosmos that still keep state in Variables, and that the stack does not use: `SeedRenderingBehavior.WHEN_SEED_CHANGES`, which keeps `cosmos_seed_checksum__…` Variables, and the watcher execution mode, whose producer keeps a backup of its XComs for its next attempt. Cosmos 1.16.0 keeps that backup in the task store of the producer on Airflow 3.3, which a user with the role User, or a role above it, may write through the REST API of Airflow, writes a `cosmos_xcom_backup__…` Variable only when its last write to the task store failed, and reads that Variable at the next attempt.

## The scan, the sync and the cache of Metabase

`metabase-init` keeps these on every start, in every deployment, so that a filter does not read a whole table for nothing and a repeated question does not run again ([ADR-0037](../adr/0037-serve-the-marts-as-views-over-the-core.md)):

| Setting | Default | What it does |
|---|---|---|
| `METABASE_SCAN_TIME` | `12:00` | The hour of the daily scan of the values of fields, as `HH:00` in UTC. |

- **The scan.** Once a day, Metabase reads the values of each field whose `has_field_values` is `list` and that someone used in the last 14 days ([The values of a field](describe-the-marts.md#the-values-of-a-field)). The scan runs after the nightly load, so that a new value reaches the filters the same day: the default is the first whole hour at least one hour after the start of the DAG `agoranomos_google_ads_daily`, at 10:37 UTC. Metabase 0.64.1 starts a daily scan at the start of an hour and drops a minute that it gets, so the setting is a whole hour, and `./agoranomos preflight` and `metabase-init` stop on any other value.
- **The sync.** Metabase looks at the tables and fields of the warehouse each hour, at the minute that it drew for the connection. A sync that someone made less frequent is hourly again at the next start, at minute 50.
- **The cache.** The policy of the whole instance, the only level of Metabase OSS, is Adaptive: a saved question or a card that takes more than 1 second on average stays in the cache for 10 times what it takes. Metabase records the average with a delay of some seconds, so the first runs of a new question do not come from the cache yet.

A schedule or a policy that someone changes in Admin > Databases or Admin > Performance goes back at the next start, and one line of `./agoranomos logs metabase-init` says so, with the value that it replaced. Metabase keeps no record of who set a schedule, so a new `METABASE_SCAN_TIME` shows the same line, the revert of an edit.

## Public links

Metabase can give a question or a dashboard a public link, which anyone who has it opens without signing in. Metabase 0.64 allows them by default; `metabase-init` turns them off once, when it sets up a new Metabase, and an admin may turn them on again in Admin > Settings > Public sharing. A public link shows its question or dashboard with the values of the filters in its address, and whoever has the link can take them out of the address and see what the filters hid. A Metabase set up before this release keeps the setting that it had, so before you turn server mode on for one, check Admin > Settings > Public sharing. `metabase-init` tries three times, two seconds apart, at the first start: if all three fail, its error, which `./agoranomos logs metabase-init` shows (`./agoranomos up` does not print it), says that the links are still on and where to turn them off, and no later start tries again, so turn them off in Admin > Settings > Public sharing. The same holds if `metabase-init` stops between creating the admin and turning the links off, for any reason, such as a lost answer to the setup call: a later start finds the admin, does not try again and prints no error, so check Admin > Settings > Public sharing.

## The metadata of the marts

The display names and descriptions of the tables and fields of the marts in Metabase, and the semantic types and `has_field_values` of the fields, come from the dbt project ([Describe the marts](describe-the-marts.md)). On every start, the one-shot job `metadata-export` exports them from dbt, and `metabase-init` applies them, with the overrides of this deployment; `demo-init` applies them too, after its sync ([ADR-0016](../adr/0016-keep-the-metadata-of-the-marts-as-code.md)).

The overrides are in `metadata/overrides.toml` in the extensions folder, which releases never change, and the file is optional. Each entry names a table of the marts, `[marts.<table>]`, or a column of one, `[marts.<table>.columns.<column>]`, with any of three properties ([Rename a field or add your own definitions](../how-to/rename-a-field.md)):

| Property | What it does | At most |
|---|---|---|
| `display_name` | Replaces the display name of the release. One line. | 100 characters |
| `description` | Replaces the description of the release. | 2,000 characters |
| `note` | Follows the description of the release after an empty line, so that a better description of a later release still reaches Metabase. | 2,000 characters |

```toml
[marts.ad_stats_campaign_daily.columns.conversions]
display_name = "Purchases"
note = "In this business, a conversion is a paid order in the online shop."
```

Each value is a text in quotes, and the file has at most 256 KiB. A table, a column or a property that dbt does not have, a value that is not a text or is empty, two columns of a table with one display name, and a mistake in the TOML are errors: the job then writes nothing in Metabase and stops with one line that names the entry, and `./agoranomos up` fails. The file is data: the jobs parse it, and nothing in it runs. Metabase OSS shows one display name for each field to everyone, so names in another language are for the whole deployment.

The code always wins. A display name, a description, a semantic type or the `has_field_values` of a field that someone changes in the Metabase UI is set back at the next start, and each change is one line of `./agoranomos logs metabase-init`, and on the first start with the demo also of `./agoranomos logs demo-init`, which applies the metadata of the marts of the demo once the demo pipeline has built them: a first fill, an update from the code, or the revert of an edit, with the value that it replaced. A semantic type of `type/Category` counts as a first fill: the analysis of Metabase gives it by itself to a column of few values, and nothing tells it from the same type set by hand. So does a `has_field_values` that Metabase can show for a field that nobody set: `search` for a text, `none` for anything else, and `list` for a text, a whole number or a yes or no. A `list` that someone set on a text goes back all the same, with a line that calls it a first fill. A line is written as soon as its change is made, so the log keeps it also when a later step of the job fails. What the code does not declare, such as whether a field is hidden, stays as it is. `./agoranomos metadata diff` prints what the next start would change, and changes nothing ([Command line](command-line.md#metadata)).

A mart, or a column that a release adds or renames, reaches the warehouse at the start that brings the release: `marts-init` builds the views of the marts before `metabase-init` runs, which syncs them and applies their metadata ([The views of the marts](#the-views-of-the-marts)). A mart that is not in the warehouse, as when `marts-init` was left out by a plain `docker compose up` of one service, gets a note in the log of `metabase-init` that says so, and the start after the build applies its metadata.

## The views of the marts

The marts are views over the core ([ADR-0037](../adr/0037-serve-the-marts-as-views-over-the-core.md)), and a run of the transform leaves a view that exists as it is, with its oid, its grants and its comment: a rebuild takes a lock that waits for a long question of Metabase and stops every reader behind it ([The data model](data-model.md#the-marts)). So the views of a release, and a new reporting currency, reach the warehouse at `./agoranomos up`: its one-shot job `marts-init` runs after `db-init` has applied the migrations of the core, and `metabase-init` waits for it ([ADR-0039](../adr/0039-run-one-dbt-build-in-the-watcher-mode.md), [ADR-0044](../adr/0044-keep-the-core-for-good-and-change-it-by-migrations.md)). It runs dbt of the Airflow image as `transformer`, the one secret that it holds, as nobody, on the network of the databases alone, with the dbt project read-only (`metabase/marts_init.py`). What it builds depends on the warehouse:

- **The snapshot that the views read exists**, the versions of the campaigns of the core that `ad_campaign_names` reads, as after the first start: the views of the marts alone, `dbt run --select marts --vars '{rebuild_views: true}'`. Their tests run in the next run of the transform, as data to fix is no reason to keep the stack from starting.
- **They do not**, as in a new warehouse or one of v0.4: `dbt build --select +marts --vars '{rebuild_views: true}'`, the seeds, the views of staging, the models of the core and the snapshots that the views read, in the order of the graph and with their tests, over the loads that the transform has pinned, none in a new warehouse, and over empty settings and sources while no load has written them. It builds that snapshot, so the next start takes the first way.
- **The rates of the core are of another reporting currency only**, as after a change of `AGORANOMOS_REPORTING_CURRENCY`: it also runs `core_fx_rates_daily` with `--vars '{recompute_rates: true}'`, which computes every day of the rates in the new currency, and the views take the new currency as they are built again. The rows of the earlier currency stay ([The rates](data-model.md#the-rates)).

It does not overlap with a run of the transform, which `max_active_runs` of Airflow does not keep from a service outside Airflow: it holds an advisory lock of PostgreSQL, exclusive, for the whole of its build, and every model, seed and snapshot of a run of the transform takes the same lock, shared, in the transaction in which it writes, as the pin does through all of its transactions (`dbt/macros/marts_init.sql`). So `marts-init` waits for the nodes that write when it starts, at most 11 minutes, and says so in one line of its log, and a node that comes after it waits for it, at most 10 minutes, the execution timeout of a task of the transform. dbt by hand takes no lock.

Once dbt has ended well, it drops the relations of earlier releases that no model builds or reads and that a build of dbt does not take with it, each by its name and kind, never by a pattern, and names each in its log, such as `dropped the table staging.int_ad_stats_ad__unioned of an earlier release, which no model builds or reads`; when there is none, it says nothing of them. Today they are three relations of v0.4 ([Upgrading from v0.4](data-model.md#upgrading-from-v04)): the tables `staging.int_ad_stats_ad__unioned` and `staging.int_ad_stats_ad_group__unioned` and the view `staging.int_ad_platforms__unioned`. A relation of one of those names and of the other kind stays, and so does one that a view of yours reads, as the job drops nothing with cascade: a line of its log that starts with `marts-init: warning:` names it and says why, the job still succeeds, and the next start tries again.

`./agoranomos logs marts-init` shows what it built, with the lines of dbt, and what it dropped. When dbt fails, or the lock does not come, the job fails with one line, `./agoranomos up` names it, and Metabase keeps the metadata and the content of the start before until a start that succeeds. A run of it by hand builds the views again: `docker compose run --rm --no-deps marts-init`.

## The content of the package

The content that agoranomos ships in Metabase is in the collection **agoranomos** at the root, with a collection in it for each package of the content: today **Demo**, which `demo-init` makes with the `demo` profile ([See the demo](../how-to/see-the-demo.md)). The collection **Agoranomos demo** of v0.1, the one whose dashboard the account of `demo-init` made, moves into it as **Demo** at the first start of v0.2.0, once, after everything in it that the demo does not ship, the trash included, has gone to the root ([See the demo](../how-to/see-the-demo.md#what-later-starts-do)). As with the metadata of the marts, the code wins ([ADR-0018](../adr/0018-keep-the-content-of-the-package-in-metabase-as-code.md)):

A stack from before the name went to lower case keeps the name of its warehouse connection and of its groups. Its collection takes the new name at the next start, and so do the descriptions of the content, each with a line `revert of an edit` in the log of `metabase-init`, which is expected.

- **View only.** On every start, `metabase-init`, and `demo-init` after it, give every group but Administrators at most View on **agoranomos** and on every collection in it, at any depth, the groups that a deployment made itself included: Curate becomes View, with one line of the log for each permission that a job lowers, such as `lowered: group "All Users" on collection "Demo": curate -> view`, and No access stays. A job locks each collection that it makes right after Metabase made it, as a new collection takes the permissions of its parent, and All Users may curate the root of a new Metabase; should anything reach it before the lock, the job puts the collection in the trash with it and stops with one line, and the next start makes it again. So only an admin can put anything into **agoranomos**. When the permissions change twice while a job lowers them, it stops with one line rather than leave the content unlocked.
- **Put back as the code says.** Each start of `demo-init` compares each item of the demo with the code: the names and descriptions of the collection, the questions and the dashboards, where each of them is, the type and the whole query of each question, with the template tags of its filters, all its settings of display, its parameters (none: Metabase shows its filters from the template tags), the dashboard that it belongs to (none) and the metadata of the columns of its answer, which must be exactly what Metabase makes for the columns that the code declares: what it computes from the query, or what it records after a run of the question, with the keys and the statistics of the data that it adds then; an edit there could give a column another name, display name or description, and each card of a dashboard whole, with its question, its place, its settings of display, such as a click behavior, its filter mappings and its series, and the filters, with their defaults, and the tabs of the dashboard. It puts back what differs, a setting that someone added included, with one line for each change, such as `revert of an edit: question demo/spend-by-day name: "My spend" -> "Spend by day and platform"`. An item in the trash comes back to its place (`restored from the trash`), and one that was deleted for good is created again (`created again`). Metabase keeps the version that a job replaced in the history of revisions of the item.
- **What is retired.** An item that a release no longer ships goes to the trash, with a line that starts with `retired`, and leaves the registry. An admin can restore it from the trash and move it out of **agoranomos**.
- **Admins.** Metabase lets an admin change everything, so an admin's edit holds until the next start, which puts it back and logs it. To keep a variant, copy a dashboard, with copies of its questions, into a collection of your own.
- **What the jobs leave.** They change only the items of the package. Anything else that an admin puts into **agoranomos** or into the collection of a package stays as it is, and a collection or a question of the same name that someone else made is never taken for one of the package. The one move of v0.1 takes a collection of the old name only with the dashboard that the account of `demo-init` made, and only its own questions of the names of v0.1.
- **The registry.** The jobs find the items of the package by the entity IDs that Metabase gave them. Metabase 0.64.1 lets no caller of its API choose an entity ID, so the jobs keep the entity ID of each item of the package, by the key of the item in the code, in a registry. It is the file `/var/tmp/agoranomos-content.json` on the volume `metabase-content`, which only `metabase-init` and `demo-init` mount, and `CONTENT_REGISTRY`, which names it, is fixed in `compose.yaml`. The file holds keys, models and entity IDs, and no secret. A file there that is not a registry of the content stops both jobs before they write anything, with one line that says to move it away; the next start then creates the content again next to the old one. A backup does not hold the registry: [Restore on a new server](../how-to/back-up-and-restore.md#restore-on-a-new-server) says what that means.

## The settings of the model

The model of advertising statistics reads two settings files of the deployment, in `model/` in the extensions folder, which releases never change ([The data model](data-model.md)). Both are optional.

| File | What it holds |
|---|---|
| `clients.toml` | The clients of the business, `[clients.<id>]` with a `name`, and the ad accounts of each, `[[accounts]]` with `platform`, `account_id` and `client` ([ADR-0024](../adr/0024-one-deployment-is-one-business.md)). An account that the file does not name belongs to the client `unassigned`. |
| `conversion_actions.toml` | Which conversion actions count in the `conversions_primary` of a campaign: `[[actions]]` with `platform`, `conversion_action_id`, `is_primary` and, optionally, `conversion_category`; an entry sets whether the action is primary, and its category when it names one, in place of the row of the base package, or of what a Google Ads account says, for the same action ([ADR-0025](../adr/0025-model-advertising-statistics-once.md)). |

The first task of each run of `agoranomos_demo_transform`, `load_settings`, reads both files, with the clients of the demo from a file of the same form in the base package, checks them and loads them as the `loader` role into `raw_settings`, in place of what was there; the dbt run that follows uses them. So a change takes effect at the next run of the transform, which you can trigger in Airflow, and needs no `./agoranomos up`. The Airflow services mount the folder read-only.

Each file is UTF-8 TOML of at most 256 KiB. A client ID is lower-case letters, digits, `-` and `_`, at most 64 characters, starting with a letter or a digit, and `unassigned` is reserved; a name is one line of at most 100 characters, and an account ID or an action ID at most 200. A key that the file does not allow, an account or an action listed twice, an account of a client that the file does not name, a text over its limit or with control characters, and a mistake in the TOML are errors: the task fails with one line that names the file and the entry, such as `clients.toml: [clients.Acme]: a client ID is lower-case letters, digits, - and _, at most 64 characters`, nothing is written, no task of dbt runs, and the marts keep their data. The line names a key or an ID of the file only where it says where the mistake is, and repeats no value. The files are data: the task parses them, and nothing in them runs.

| `PLATFORM_POSTGRES_PASSWORD` | The superuser of the platform PostgreSQL | As for `WAREHOUSE_POSTGRES_PASSWORD`. |
| `AIRFLOW_DB_PASSWORD` | The role that owns the metadata database of Airflow | Change it and run `./agoranomos up`: the role gets the new password. |
| `METABASE_DB_PASSWORD` | The role that owns the application database of Metabase | As for `AIRFLOW_DB_PASSWORD`. |
| `METABASE_READER_PASSWORD` | The read-only role that Metabase reads the warehouse as | As for `AIRFLOW_DB_PASSWORD`; Metabase's connection is updated too. |
| `WAREHOUSE_LOADER_PASSWORD` | The role for loading data into the raw schemas of the warehouse (dlt) | As for `AIRFLOW_DB_PASSWORD`. |
| `WAREHOUSE_TRANSFORMER_PASSWORD` | The role for building the staging and marts schemas of the warehouse (dbt) | As for `AIRFLOW_DB_PASSWORD`. |
| `BACKUP_DB_PASSWORD` | The role that takes the backups, on both instances: it reads every table and writes nothing ([ADR-0020](../adr/0020-back-up-the-databases-every-day.md)) | As for `AIRFLOW_DB_PASSWORD`. |
| `VALKEY_PASSWORD` | The password of the Celery broker, used only with CeleryExecutor | Change it and run `./agoranomos up`. |

| `AIRFLOW_AI_PASSWORD` | The password of the Airflow user `ai`, with the role Viewer, as which the MCP server of Airflow signs in | Change it and run `./agoranomos up`: `airflow-init` gives the user the new password. |
| `CELERY_RESULTS_DB_PASSWORD` | The role that owns the database of the results of Celery, used only with CeleryExecutor: the worker writes the state of each task there, and holds no password of the metadata database of Airflow | As for `AIRFLOW_DB_PASSWORD`. |
| `AIRFLOW_FERNET_KEY` | The key that encrypts the connections and variables saved in Airflow | Do not change it: what Airflow saved could no longer be decrypted. |
| `AIRFLOW_JWT_SECRET` | The key that signs the API tokens of Airflow | Change it and run `./agoranomos up`; people have to sign in again. |
| `AIRFLOW_API_SECRET_KEY` | The secret key of the Airflow API server | As for `AIRFLOW_JWT_SECRET`. |
| `AIRFLOW_ADMIN_PASSWORD` | The password of the Airflow user `admin`, set on the first start | With the `demo` profile, `demo-init` signs in with it on every start. If you change the password in Airflow, put the same value here. |
| `METABASE_ENCRYPTION_KEY` | The key that encrypts the connection details saved in Metabase | Do not change it: Metabase could no longer read its saved connections. |
| `METABASE_SESSION_KEY` | The key that signs the sessions that Metabase keeps in its application database, so that whoever can read or write that database cannot make a session of their own. At least 16 characters: Metabase does not start with a shorter one | Change it and run `./agoranomos up`: everyone has to sign in to Metabase again. The first start of a release that adds it signs everyone out once, the same way. |
| `METABASE_ADMIN_PASSWORD` | The password of the Metabase admin account | The first-start setup signs in with it on every start, and so does `demo-init`. If you change the password in Metabase, put the same value here. |

On every start, the setup job `db-init` sets each role of the warehouse (`loader`, `transformer`, `metabase_reader` and `ai_reader`, which is `NOLOGIN` while `WAREHOUSE_MCP` is off), of the platform instance (`airflow`, `metabase` and `celery_results`), and `backup`, which both instances have, to `LOGIN`, with no `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION` or `BYPASSRLS` attribute, and gives it the password from `.env`. So if you give one of these roles such a power by hand, the next `./agoranomos up` takes it back. On both instances, no role but the superuser can connect to the `postgres` and `template1` databases or read the statistics of the statements (`pg_stat_statements`): `airflow`, `metabase` and `celery_results` connect only to the database that each owns, and the roles of the warehouse only to `warehouse`. `backup` is a member of `pg_read_all_data`; on the warehouse instance (`warehouse-db`) it connects to `warehouse` only, and on the platform instance (`platform-db`) to `airflow` and `metabase` only, in sessions that start read-only. It reads no statistics of the statements either: `pg_read_all_data` lets it select from the views of `pg_stat_statements`, but the functions behind them stay closed to it. `db-init` also gives `loader` and `transformer` a lock timeout of one minute: a statement that waits longer for a lock fails with `canceling statement due to lock timeout`. A load then fails and is tried again instead of waiting without end. A dbt run fails too, and the mart keeps its data: dbt renames a table that it rebuilds, which waits for the queries that read the table, and the queries that come later, such as those of Metabase, wait behind it.

`db-init` gives `ai_reader` sessions that start read-only, a statement timeout of one minute, the same timeout for a transaction left open, and a limit of three connections; it reads `marts`, whose views read the core as their owner, `transformer`, and no other schema: neither `staging`, whose views stand over a raw layer that is to be erased, nor the core, a raw schema or `ops` ([ADR-0043](../adr/0043-define-the-metrics-in-the-warehouse-and-give-agents-tools-over-the-marts.md)). A warehouse of an earlier release, where it also read `staging`, loses that with its next `./agoranomos up`. `db-init` also gives `metabase_reader` a statement timeout of five minutes and a limit of 20 connections. A question or a dashboard card whose query runs longer fails with `canceling statement due to statement timeout`, before the query timeout of Metabase itself, 20 minutes; and Metabase, whose pool holds up to 15 connections to the warehouse, cannot take the connections that the pipelines need (both defaults of Metabase 0.64.1, as of October 2026).

`celery_results`, which only the CeleryExecutor variant uses, owns the database of the results of Celery on the platform instance: the worker writes the state of each task there, and the scheduler reads it, so the worker holds neither the password of the metadata database of Airflow nor the key that signs its tokens. That narrows what the worker holds, but does not keep the code of a task away from the scheduler, which loads the results as pickles ([ADR-0015](../adr/0015-run-localexecutor-by-default.md) says how). The code of a task can read the password of the role, so `db-init` gives it a limit of 20 connections, which keeps such code from taking the connections of the instance from Airflow and Metabase. Each process of a worker that has run a task keeps one of them open: `AIRFLOW_WORKER_CONCURRENCY` processes per worker; the scheduler opens one more when it reads, and so does `db-init`. On every start, `db-init` also deletes the results older than 90 days, which nothing in Airflow removes from that database. It does so as `celery_results`, never as the superuser, since whoever holds the password of the role decides what runs in its database; when the deletion fails, `db-init` says so and the start goes on.

`AIRFLOW_DB_PASSWORD`, `VALKEY_PASSWORD` and `CELERY_RESULTS_DB_PASSWORD` are written into connection URLs. If you choose them yourself instead of letting `init` generate them, use letters and digits only: a character such as `@`, `/` or `:` breaks the URL.

The warehouse has one more role, `migrator`, which owns the schema `core` and has no password: on every start `db-init` sets it to `NOLOGIN`, with none of the attributes above and no password, gives it no privilege, and becomes it only to apply the migrations of the core ([The migrations of the core](#the-migrations-of-the-core)).

## The migrations of the core

The tables of the schema `core` ([The schema core](data-model.md#the-schema-core)) come from numbered SQL files in `postgres/migrations`, which `db-init` applies once each ([ADR-0038](../adr/0038-load-by-copy-and-write-the-core-by-whole-days.md), [ADR-0044](../adr/0044-keep-the-core-for-good-and-change-it-by-migrations.md)). A file is named `NNNN_name.sql`: four digits, from `0001` with no gap and no duplicate, an underscore, and a name of lower-case letters, digits and underscores. On every start, after it has set up the roles and the schemas, `db-init`:

1. checks the names and the numbers of the files;
1. reads the migrations that the warehouse has applied from `core.schema_migrations`, which the first migration creates, so that a warehouse without that table, such as one of v0.4.x, has applied none;
1. checks that each of them is still in `postgres/migrations` under the same name and with the same SHA-256 of its bytes;
1. applies the others in the order of their numbers, each in a transaction of its own, as the role `migrator`, with a lock timeout of one minute, and with its row in `core.schema_migrations`: the migration and its row commit together or not at all (`postgres/migrate.sql`).

`db-init` logs each migration that it applies, or that none waits, so a second start applies nothing. It stops before it applies anything, and `./agoranomos up` fails, when a file has a wrong name or number, when a migration that the warehouse has applied has changed, also in its line endings only, or when the warehouse has applied a migration that the checkout lacks, as after a newer release or the rename of a file; `./agoranomos logs db-init` names the file. A migration that fails stops it too, and leaves nothing of itself behind. So an applied migration never changes, and a change of the core is a new migration. The checkouts of macOS, Linux and WSL2 give a file the same bytes, as `.gitattributes` gives every text file LF line endings. A warehouse that a newer release has migrated goes on with a checkout of that release, or goes back with a backup made before the migration, which `./agoranomos restore` puts back with the checkout of the release before ([Back up and restore](../how-to/back-up-and-restore.md)): the `db-init` that `restore` runs before `pg_restore` gets `DB_INIT_MIGRATIONS=skip` and leaves the migrations alone, as `pg_restore` replaces the warehouse whole, and the `db-init` of the start at the end of the restore applies those that the restored warehouse lacks, or stops on a warehouse that a newer release migrated. `DB_INIT_MIGRATIONS` is no setting of `.env`: `compose.yaml` does not pass it, so every other start applies the migrations. `./agoranomos up` takes that backup by itself ([ADR-0044](../adr/0044-keep-the-core-for-good-and-change-it-by-migrations.md)): before `db-init` runs, it compares the files with `core.schema_migrations`, and when some wait and the warehouse holds data, it takes a backup by hand whose manifest names them, and stops before `db-init` when that backup fails ([The backup before a migration of the core](../how-to/back-up-and-restore.md#the-backup-before-a-migration-of-the-core)). A new warehouse holds no data and gets no backup.

[`./agoranomos status`](command-line.md#status) shows how many migrations the warehouse has applied, the last of them with its time, and those that wait for the next `./agoranomos up`.

## Back up Metabase before an upgrade

A release that moves Metabase to a new major version, such as from 0.63 to 0.64, migrates the application database of Metabase, the `metabase` database of `platform-db`, at the first `./agoranomos up`. Do not count on undoing the migration: as of October 2026, Metabase 0.63.19 refuses to start on a database that 0.64.1 has migrated, and after the `migrate down` command of 0.64.1 it fails on a migration of its own. The way back is a backup made before the upgrade. A large application database can take a while to migrate, because 0.64 changes the primary key of the `query_execution` table, which logs the queries that Metabase runs, and splits that table into partitions.

Before the first `./agoranomos up` of the new release, while the stack of the release that you come from runs, note the commit that you come from, which `git rev-parse HEAD` prints, and take a backup:

```bash
./agoranomos backup
```

It prints the name of the backup, such as `20261011T030012Z`, which `./agoranomos status` shows too ([Command line](command-line.md#backup)). Later backups, scheduled or by hand, do not remove it: the retention removes scheduled backups only. Then update the checkout and run `./agoranomos up`, which starts the new version; `./agoranomos logs metabase` shows the migration.

To go back, return the checkout to the commit that you came from, which pins the earlier version of Metabase, and restore the database of Metabase from the backup. Airflow migrates its database one way too, so see first whether the update also changed the Airflow image, while the checkout is still at the new release:

```bash
git diff <the commit that you came from> HEAD -- airflow/Dockerfile | grep '^[-+]FROM'
```

It prints the old and the new `FROM` line of the Airflow image when Airflow changed, and nothing otherwise. When it prints nothing, restore the database of Metabase alone. When it prints the lines, restore `metabase,airflow`, or `airflow-init` fails on the schema of the newer Airflow; you lose the runs of Airflow since the backup. Return the checkout, then run:

```bash
./agoranomos restore 20261011T030012Z --only metabase
# when the Airflow image changed as well:
./agoranomos restore 20261011T030012Z --only metabase,airflow
```

`restore` checks the backup before it changes anything: every file against its SHA-256, and each dump that it restores read to its end. A check of the table of contents alone, with `pg_restore --list`, passes a dump that was cut short after it, and a restore from such a dump would drop the database and leave it without its rows. Then `restore` stops the services that use the databases, restores the database with its owner and its access rights, and starts the stack ([Command line](command-line.md#restore)). Everything that Metabase saved after the backup is lost. If `restore` stops because the images of the backup differ from those of the checkout, the checkout is not at the commit that you came from.
