# Extensions

This folder holds what this deployment adds to agoranomos: its own DAGs, its own words for the metadata of the marts and the settings of its model today, and its own dbt models and data sources once the stack supports them ([ADR-0013](../docs/adr/0013-keep-extensions-apart-from-the-base-package.md)). Releases of agoranomos never overwrite or delete what you put here, and git ignores everything in this folder except this file, so updates leave your work alone.

- `dags/`: Airflow DAGs. Airflow loads them as the `extensions` DAG bundle, next to the `agoranomos` bundle of the base package. A new file appears in Airflow within about a minute.
- `metadata/overrides.toml`: this deployment's own names, descriptions and notes for the tables and fields of the marts in Metabase ([Rename a field or add your own definitions](../docs/how-to/rename-a-field.md), [ADR-0016](../docs/adr/0016-keep-the-metadata-of-the-marts-as-code.md)). It is data: `metabase-init` and `demo-init` read it, check it before they write anything, and apply it on every start, and nothing in it runs.
- `model/clients.toml` and `model/conversion_actions.toml`: this deployment's clients and the ad accounts of each, and which conversion actions count as conversions ([The data model](../docs/reference/data-model.md#clients), [ADR-0024](../docs/adr/0024-one-deployment-is-one-business.md)). They are data: the first task of the transform reads them, checks them before it writes anything, and loads them on every run of the transform, and nothing in them runs. A mistake in a file fails that task with one line that names the file and the entry, and the marts keep their data.

Keep this folder in a git repository of your own, so that changes, including those made by AI agents, have a history and can be reviewed. Code here runs on the same Airflow workers as the DAGs of agoranomos, with the same permissions: a task can read the environment of the process that runs it, which holds keys of Airflow, the passwords of the warehouse roles `loader` and `transformer` (`WAREHOUSE_LOADER_PASSWORD`, and `WAREHOUSE_TRANSFORMER_PASSWORD` as `DBT_ENV_SECRET_WAREHOUSE_PASSWORD`), and, with the LocalExecutor, where the scheduler runs the tasks, the password of the metadata database of Airflow. With the CeleryExecutor, the worker holds neither that password nor the key that signs the tokens of Airflow, but a task on the worker can read the password of the Valkey broker, which is part of `AIRFLOW__CELERY__BROKER_URL`, and that of the database of the results of Celery, part of `AIRFLOW__CELERY__RESULT_BACKEND`, which opens no other database. With it, a task can write a result that runs code in the scheduler, which loads the results as pickles and holds that password and that key. Review it as you would review any code that touches your data.

To keep extensions somewhere else, set `AGORANOMOS_EXTENSIONS_DIR` in `.env`.
